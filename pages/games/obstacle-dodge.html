Status Prototype

Overview

Obstacle Dodge is a fast-paced arcade dodge game prototype. The player must avoid obstacles that drop from above, fly homing toward them, and spin. With multiple obstacle types featuring varied movement patterns, the game tracks score over time utilizing a simple, colorful visual style.

Your Contribution

This prototype focused on maximizing code reuse through Unity's component architecture:

  • Obstacle Archetypes via Component Composition: Designed multiple distinct obstacle behaviors (Dropper, FlyingAtPlayer, Mover, Spinner) as completely separate, tiny MonoBehaviour scripts that can be mixed and matched on prefabs without inheritance chains.
  • Homing Obstacles: Implemented FlyingAtPlayer, caching the player's Transform and using Vector3.MoveTowards to persistently track the player over time.
  • Color Palette System: Created a scalable color theming system using a Colors asset folder to dynamically swap palette materials and keep the visuals interesting with minimal art requirements.
  • Hit Response & Scorer: Developed the collision response triggers and time-based score tracking system.

Media & Iteration

Technical Deep-Dive

Multiple Obstacle Archetypes via Composition

A dodge game needs interesting variety without creating large bloated obstacle classes. Each behavior was implemented as its own small MonoBehaviour. Unity's component model allows mixing behaviors on prefabs without inheritance chains — adding a Spinner and a FlyingAtPlayer script onto the same GameObject instantly creates a homing, spinning obstacle with zero extra code.

Homing Obstacle Logic

A homing obstacle needs to persistently update its direction toward a moving player. FlyingAtPlayer caches the player Transform reference on Start() and uses Vector3.MoveTowards (or Vector3.Lerp) each frame to smoothly close the distance, resulting in a relentless, curving flight path.

Postmortem / Lessons Learned

What went well

  • Component composition worked exactly as intended. Having each obstacle behavior as its own tiny script meant creating new obstacle variants was just a matter of combining components on a prefab — no code changes required. The homing spinner, for example, was created in the editor with no new scripting.
  • The color system kept the game visually interesting with minimal art. Using a Colors/ asset folder and swapping palette materials gave each session a different look without needing any additional art pipeline.

What I'd do differently

  • Add version control and a build from the start. Without git history or a build, there's no way to see how the project evolved or to share a playable version without opening Unity. Even a basic GitHub repo and a WebGL build would make this instantly shareable.
  • Add a difficulty curve and a proper game loop. The prototype has obstacles but no escalating spawn rate, no timer, and no clear win condition beyond avoiding hits. I'd define the full game loop.
