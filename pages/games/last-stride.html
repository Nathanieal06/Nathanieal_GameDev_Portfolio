Overview

LastStride is an endless runner featuring procedural chunk-based level generation, multiple obstacle types, distinct biomes with per-biome background music, boss encounters, and increasing speed difficulty scaling over time.

Your Contribution

I built the game's core architecture and procedural generation systems:

  • Procedural Level Generator: Designed a chunk lifecycle system where chunks scroll toward the player and respawn seamlessly. Transitions handle biomes, speed scaling, and boss encounters.
  • Chunk System & Lane Safety: Implemented self-contained level segments that spawn obstacles randomly but safely across 3 lanes, ensuring impossible configurations are mathematically prevented.
  • Boss Fight System: Developed a boss encounter that moves alongside the world and uses a laser attack to clear chunk obstacles in real-time.
  • Audio & Memory Management: Built an audio manager that preloads all biome BGM clips into RAM at startup to eliminate mid-run disk I/O and lag spikes during transitions.
  • Player Controller: Programmed a 3-lane movement system with smooth lerp-based lane switching, jumping, sprint, and collision responses.

Media & Iteration

Technical Deep-Dive

Biome-Based Proc-Gen with BGM Preloading

An infinite runner needs variety across long sessions. Biome transitions must change music without causing lag spikes from loading audio mid-run. To solve this, all biome BGM clips are preloaded into RAM on Start(). Biome transitions are triggered by chunk count intervals. This deliberate performance optimization ensures a perfectly smooth player experience. 

// LevelGenerator.cs — Preloading all biome BGM at startup
// "Preload all biome BGM clips into RAM at startup so biome transitions cause zero lag"
AudioClip[] allClips = new AudioClip[biomes.Length];
for (int i = 0; i < biomes.Length; i++) allClips[i] = biomes[i].bgmClip;
AudioManager.Instance.PreloadClips(allClips);

Lane-Safe Obstacle Spawning

Random lane selection can produce impossible configurations where all 3 lanes are blocked simultaneously. The solution uses an availableLanes list that starts as [0, 1, 2]. Each call to SelectLane() removes the chosen index from the list, guaranteeing no lane is used twice per chunk to ensure the player always has an out. 

List<int> availableLanes = new List<int> { 0, 1, 2 };
int SelectLane() {
    int idx  = Random.Range(0, availableLanes.Count);
    int lane = availableLanes[idx];
    availableLanes.RemoveAt(idx);
    return lane;
}

Postmortem / Lessons Learned

What went well

  • The lane-safety system solved a real fairness problem cleanly. Using a shrinking availableLanes list to prevent impossible obstacles was simple to implement and worked perfectly — players always have at least one safe lane available.
  • BGM preloading eliminated all biome transition lag. Deliberately preloading all audio clips at startup rather than loading on biome change removed what would have been a noticeable stutter during intense gameplay — a small decision with a big player-experience payoff.

What I'd do differently

  • Use an object pool for chunks instead of Instantiate/Destroy. Instantiating and destroying chunks each cycle creates GC pressure. A proper object pool (reuse inactive chunks) would be cleaner, especially if expanding to mobile where memory management matters more.
  • Design the biome system data-first with ScriptableObjects. The current Biome struct is configured in the inspector. Using ScriptableObject assets would make adding new biomes (new chunk prefabs, music, obstacles) a pure content task with no code changes.
