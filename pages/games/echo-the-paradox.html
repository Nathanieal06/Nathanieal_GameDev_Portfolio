Overview

Echo: The Paradox is a first-person narrative adventure and walking simulator set across 4 acts. The player responds to a radio distress call, interacts with objects and NPCs, makes story choices, and experiences a mystery narrative. There is a strong emphasis on atmosphere, dialogue, interactables, and scripted sequences.

Your Contribution

As the sole developer, I implemented the game's architecture and narrative systems:

  • 4-Act Narrative Structure: Divided the game into 4 separate Unity scenes (each ~74MB with fully baked GI). Each act has its own sequence manager and objective tracker utilizing coroutines to manage timed event sequences.
  • Interactable Object System: Created a generic interaction system using an IInteractable interface, completely decoupling the player raycasting logic from concrete interactables like doors, chests, and radios.
  • Dialogue / Conversation System: Integrated a branching dialogue system using DialogueEditor, with timed delays between conversation phases, ambient audio, and story choice tracking that persists across acts.
  • Layered Audio & UI: Layered radio SFX, ambient static, and dialogue audio simultaneously, and managed all UI states through a central UIManager.
  • Scene Transitions: Built smooth fade-to-black scene transitions with title cards using async loading to mask load times between the large baked scenes.

Technical Deep-Dive

Coroutine-Based Scripted Story Sequences

A narrative game requires scripted sequences where events happen in a specific order with precise timing — radio plays, player reads map, dialogue fires, scene transitions after delay — without a visual scripting tool. Each act has a dedicated sequence manager using Unity coroutines. DialogueSequenceManager tracks a sequence step int and advances through states as the player completes objectives. 

// DialogueSequenceManager.cs — Sequence orchestration
[Header("Conversations")]
[SerializeField] private NPCConversation radioConvo01;
[SerializeField] private NPCConversation radioConvo02;
[SerializeField] private NPCConversation radioResponseConvo;

[Header("Sequence Delays")]
[SerializeField] private float delayBeforeConvo02    = 10f;
[SerializeField] private float delayBeforeResponse   = 15f;

[Header("Scene Transition & Effects")]
[SerializeField] private string nextSceneName        = "Act02";
[SerializeField] private Image  fadePanel;
[SerializeField] private string fadeTitleText        = "Act 02: The Rescue";
[SerializeField] private float  fadeDuration         = 2f;

Interface-Based Interactable System

Many object types (doors, chests, radios, beds, maps) all need to be interactable but behave completely differently. By using an IInteractable interface with a single Interact() method, PlayerInteraction only needs to know about the interface. It never references concrete types, meaning new interactable types can be added without touching the player code at all. 

// IInteractable.cs — Contract
public interface IInteractable { void Interact(); }

// PlayerInteraction.cs — Fully decoupled
if (Physics.Raycast(ray, out hit, interactRange)) {
    IInteractable interactable = hit.collider.GetComponent<IInteractable>();
    if (interactable != null) interactable.Interact();
}

Postmortem / Lessons Learned

What went well

  • The interface-based interactable system scaled perfectly. Every new interactable type I added (radio, map, door, chest, bed) slotted in without touching PlayerInteraction once. The interface design paid off completely across 4 acts of content.
  • The 4-act scene split kept things manageable. Each act being a completely independent scene meant I could open, edit, and test one act without worrying about breaking the others. No cross-scene bugs emerged during development.

What I'd do differently

  • Use version control throughout development, not just at the end. Having a single "Initial check-in" commit means there's no git record of how the game evolved. I'd commit after each act, each feature, and each major fix so the development story is preserved.
  • Use Unity Timeline or a node-based dialogue graph for the sequence managers. The coroutine-based sequence managers worked but were fragile to edit — changing the timing of one event sometimes broke subsequent steps. A visual sequencer would be far easier to iterate on during playtesting.
