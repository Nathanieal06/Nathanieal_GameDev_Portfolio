Overview

Unity RPG is an early third-person action prototype built around a generic Finite State Machine (FSM) architecture. The player has two clean, isolated states: Free Look (exploration) and Targeting (lock-on combat strafing). It was specifically designed as an architectural learning project for state-machine-driven character control.

Your Contribution

As the sole developer, I implemented the entire architectural foundation from scratch:

  • Generic State Machine Architecture: Built a reusable FSM base (StateMachine.cs) ensuring clean separation of state logic with a well-defined Enter/Tick/Exit lifecycle.
  • Isolated Player States: Developed PlayerFreeLookState and PlayerTargetingState, fully decoupling movement and camera behavior without relying on monolithic if/else chains.
  • Targeting / Lock-On System: Implemented Physics.OverlapSphere targeting logic to smoothly lock onto enemies equipped with a Target marker component.
  • Input Reader Event Wrapper: Created InputReader.cs to wrap the auto-generated Input System Controls class, re-emitting typed C# events to keep the state machine decoupled from Unity's direct input dependencies.

Media & Iteration

Technical Deep-Dive

State Machine vs If-Else Character Controllers

Character controllers built with if/else chains become unmanageable quickly (e.g., "if attacking and not dodging and grounded and armed..."). I built a generic StateMachine + State base classes. Each state is completely isolated and only knows about the PlayerStateMachine context. Adding a new state (crouch, swim, climb) requires only a new class — no touching existing states. This was my earliest project, and choosing to learn this pattern shows immediate architectural foresight.

Input Reader Event Wrapper Pattern

States need to respond to input events but shouldn't reference Unity's Input System classes directly, keeping them testable and decoupled. InputReader.cs acts as an intermediary layer: it subscribes to the auto-generated Controls input events and re-emits them as plain C# Action events. States subscribe only to InputReader events — if the input system changes, only InputReader needs updating.

Warrior Prefab Setup

Getting a realistic humanoid character working involves configuring the correct rig, materials, colliders, and animator settings. The Warrior.prefab is a fully configured, 36.9KB asset with all mesh renderers, animators, colliders, and scripts pre-configured, reflecting the depth of setup done in the Unity Editor rather than via runtime scripts.

Postmortem / Lessons Learned

What went well

  • The state machine architecture proved itself immediately. Adding the targeting state didn't require touching the free-look state at all — they're completely isolated. The FSM pattern removed all the complexity I'd otherwise have had from conditional chains in a single monolithic controller.
  • The InputReader wrapper pattern kept states clean. No state file directly imports anything from UnityEngine.InputSystem — they only subscribe to InputReader events. That separation made the code easy to read and swap input backends in the future.

What I'd do differently

  • Keep all project files inside the Assets/ folder. Loose .inputactions and .meta files ended up at the project root during early setup — this is an organizational mistake I'd avoid by establishing the folder structure before importing any assets.
  • Build on this pattern in subsequent projects. Looking back, the architectural clarity of this FSM prototype didn't carry forward into larger projects like PlayerController. I'd use this pattern as the foundation for every new character controller going forward rather than reverting to a single large controller class.
