Overview

This grid-based tactical game was built as a timed programming assessment submission. Player units and enemy units occupy a 3D grid. Enemy AI pathfinds toward the player using A*. A custom editor tool allows level designers to place obstacles on the grid without entering Play mode.

Your Contribution

Built under a strict 48-hour deadline, I implemented the following from scratch:

  • A* Pathfinding System: Implemented a full A* algorithm with a Manhattan heuristic (optimal for 4-directional grids), handling obstacle avoidance and path retracing via parent pointers without relying on Unity's built-in NavMesh.
  • Grid Manager: Developed the central grid system managing a 3D grid of Block cells, including walkability flags and neighbor lookup for pathfinding.
  • Interface-Based AI: Designed an IAI interface contract to keep Enemy units decoupled from their pathfinding logic, allowing multiple AI behaviors to be easily swapped.
  • Custom Editor Tooling: Went beyond the assessment brief by building an ObstacleEditorWindow (extending EditorWindow). This allows level designers to place obstacles on the grid during design-time without entering Play mode.

Technical Deep-Dive

A* Pathfinding from Scratch in 2 Days

Enemy units need to navigate a grid, avoiding obstacle cells, to reach the player — requiring a pathfinding algorithm built without external libraries. Using A* with a Manhattan heuristic, an open list with linear scan, a HashSet closed set, and path retracing, the algorithm correctly handles obstacle avoidance, edge traversal, and no-path scenarios. Implementing this correctly from memory during a timed assessment demonstrates strong algorithmic understanding.

Custom Editor Window for Obstacle Placement

Placing obstacles on the grid at design time without running the game was solved by writing custom Editor scripts. ObstacleEditorWindow extends EditorWindow to provide a panel in the Unity editor. ObstacleManagerEditor extends Editor with a custom inspector. New obstacles become pure design-time authoring, demonstrating Editor API knowledge beyond runtime code.

Postmortem / Lessons Learned

What went well

  • A* worked correctly on the first complete test. Having planned the open list, closed set, g-cost/h-cost structure, and Manhattan heuristic on paper before writing a single line meant the implementation came together quickly without major debugging.
  • The custom editor window impressed beyond the brief. Building the ObstacleEditorWindow as a stretch goal — allowing level design without entering Play mode — demonstrated Editor API knowledge that wasn't required but added real value to the submission.

What I'd do differently

  • Replace the linear open-list scan with a min-heap (priority queue). The current A* open list uses O(n) linear search to find the lowest-cost node. For large grids this becomes slow. A SortedSet or a proper min-heap would give O(log n) extraction and make the pathfinder scale to much larger maps.
  • Use a proper state machine for enemy turns. The current EnemyAI is stateless — it just runs FindPath and moves. For a real tactical game I'd add turn phases (move → attack → end turn) using a state machine so the game loop is clearly defined and extensible.
